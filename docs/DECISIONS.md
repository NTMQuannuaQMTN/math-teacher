# Architecture & Scope Decisions

This file documents engineering decisions made autonomously during the initial MVP sprint,
including places where the original spec was ambiguous or (due to a truncated prompt) cut off
after "MVP FEATURE 2 — AI QUESTION UNDERSTANDING". Decisions below fill those gaps using the
stated product vision (photo → understand → classify → [diagram] → solve → explain) and
standard engineering judgment. Revisit any of these with the user as needed.

## Repository shape
Monorepo, two apps:
- `app/` — Expo (React Native + TypeScript) client
- `worker/` — Cloudflare Worker (TypeScript) backend, D1 + R2

## Processing model: synchronous pipeline, single endpoint
`POST /api/questions` accepts an uploaded image and runs the full pipeline server-side
(extract → classify → optional geometry spec → solve → explain) before responding once with
the complete structured result. Alternative considered: async job + polling. Rejected for MVP
because it roughly doubles endpoint/state-machine surface for a fixed time budget, and Workers'
subrequest/wall-clock limits comfortably fit 2-3 sequential LLM calls. `status` is still stored
on the DB row (`processing` → `complete`/`failed`) so the async version is a small follow-up,
not a rewrite.

## AI provider abstraction
`worker/src/ai/provider.ts` defines an `AIProvider` interface (`extractQuestion`,
`generateGeometry`, `solve`). Two implementations exist — `OpenAIProvider` (Chat Completions API,
vision + JSON mode) and `AnthropicProvider` (Messages API) — both calling their provider directly
via `fetch` (no SDK dependency, to keep the Worker bundle small) and sharing retry/backoff logic
(`worker/src/ai/httpRetry.ts`). `worker/src/ai/factory.ts` picks the active one from the
`AI_PROVIDER` env var (`"openai"` | `"anthropic"`, default `"openai"`); route handlers only ever
see the `AIProvider` interface, never a concrete provider. Model ids are env-configurable
(`OPENAI_MODEL` / `ANTHROPIC_MODEL`). API keys live only in Worker secrets (`OPENAI_API_KEY` /
`ANTHROPIC_API_KEY`), never shipped to the client — only the key matching `AI_PROVIDER` needs a
real value.

This was originally written as an Anthropic-only implementation with the interface designed to be
swappable "in principle." It was switched to OpenAI as the active provider shortly after, which
is what motivated actually building the factory/config-switch rather than leaving the swap as a
hypothetical — see git history around the `AI_PROVIDER` var for the concrete change.

## Strict output validation
All AI JSON output is parsed with `JSON.parse` inside a try/catch and validated with Zod schemas
(`worker/src/schema.ts`) before being trusted or persisted. Invalid/unparseable output produces a
structured `422`-style pipeline failure recorded on the question row, never a silent pass-through
of raw model text into the DB as if it were structured data.

## Geometry representation: structured spec, not an image
"Interactive geometry diagram" is implemented as a small declarative JSON scene graph (points,
segments, circles, polygons, angle markers, labels, all in a normalized 0-100 coordinate space)
generated by the AI and rendered client-side with `react-native-svg`. This is what makes it
"interactive" (tap a point/label to highlight it, pinch/pan the canvas) as opposed to a static
generated bitmap, and keeps the Worker from needing an image-rendering pipeline.

## Data model (D1)
- `questions` — one row per submission: r2 key, extracted fields, classification, status, timestamps
- `geometry_specs` — one row per question needing a diagram, FK to question
- `solutions` — one row per question, FK to question
- `request_log` — minimal IP+timestamp log used for rate limiting

## Rate limiting
Simple D1-backed fixed-window counter per IP (`X-Forwarded-For` / `CF-Connecting-IP`) capped at
10 submissions / hour. Not distributed-perfect, but sufficient for an MVP behind Cloudflare.

## Auth
No user accounts in this MVP (spec lists auth as conditional: "if implemented"). Questions are
addressed by an opaque UUID returned to the client; no cross-user listing endpoint exists, so a
question is only retrievable by someone who has its id. Auth/accounts are a clearly-flagged
follow-up, not silently skipped.

## Camera vs upload in Expo
`expo-image-picker`'s camera launcher works in Expo Go on a real device (it does not require a
custom dev client) but does *not* work in the iOS Simulator (no camera hardware) and can be
restricted in Expo Go depending on OS permissions. The app offers both "Take Photo" and
"Choose from Library" and degrades gracefully (clear message, no crash) if camera permission is
denied or the camera is unavailable, per spec §5.
